速いコアと遅いコア — worker を固定するか、移動させるか

0003 の続き。M4 で「idle が消えたのに速くならなかった」謎を、コアの速さと OS の振る舞いから説明できるようになる。

0003 で残った謎

M4 で interleave を使うと、idle は 32.6% から 0.1% に消えた。

それなのに、計算時間は 4.3% しか縮まなかった。

0003 のシミュレータは「コアはみな同じ速さ」と仮定していたので、この謎を説明できない。

このレッスンでは、シミュレータにコアの速さとworker の移動を入れる。

2つの新しい部品

コアの速さ

速いコア（M4 の P コア）は速さ 1、遅いコア（E コア）は速さ r で仕事を進める。

r = 0.43 なら、遅いコアは同じ仕事に 1 ÷ 0.43 ≈ 2.3 倍の時間がかかる。

固定と移動

固定: worker はずっと同じコアで働く（Linux で taskset を使った状態）。

移動: 仕事が尽きた worker が速いコアを空けると、遅いコアで働いている worker がそこへ引っ越す（macOS のスケジューラの振る舞い）。

引っ越した worker は、途中の仕事の残りを速いコアで続ける。

触って比べる

36 頂点・重さは末尾ほど重い（soc と同じ形）。2 頂点ずつ 18 バッチに分け、速いコア 2 個・遅いコア 2 個（r = 0.43）に 4 worker で配る。

見てほしい3点

1. 固定の block は遅い

重い末尾のバッチが遅いコアに乗ると、速いコアは早く終わって待つしかない。

worker の idle も、速いコアの idle も大きい。

2. 移動ありの block は、固定の block よりずっと速い

速いコアを空けた worker の代わりに、遅いコアの worker が引っ越してくる。

worker の idle は大きいままなのに、速いコアの idle はほぼ 0 になる。

つまり worker が暇でも、速いコアは暇ではない。

3. だから M4 では「idle を消しても速くならなかった」

M4 が測っていたのは worker の idle だった。

block の idle の多くは、速いコアがすでに別の worker で埋まっている時間だったので、それを消しても速いコアの仕事は増えない。

idle% は「worker = コア」という前提を暗に置いた指標である。

Linux での実測（エミュレーション）

M4 では worker の移動を止められない。そこで Linux 上で、cgroup の CPU 時間制限で遅いコアを作って測った（soc-sign-epinions、速い×2 + 遅い×2）。

まず、worker をコアに固定した場合（3 回の最小値）。

コア構成blockinterleave短縮
速い×464.9 秒（idle 22.8%）51.1 秒（idle 0.6%）1.27 倍
速い×2 + 遅い×2（r = 0.43）83.6 秒（idle 12.4%）72.2 秒（idle 0.8%）1.16 倍
速い×2 + 遅い×2（r = 0.26）143.1 秒（idle 32.5%）81.5 秒（idle 0.4%）1.76 倍

固定なら、コアの速さが違っても idle を消した分だけ速くなる。

次に、同じ構成で worker を移動ありにした場合（2 回の最小値、別の実行器なので上の表と絶対値は少し違う）。

rblock 固定 → 移動ありinterleave 固定 → 移動ありblock ÷ interleave
0.43108.2 → 88.9 秒75.4 → 75.5 秒1.43 → 1.18 倍

移動は block だけを大きく速くし、interleave はほとんど変えない。その結果、idle を消す効果が小さく見える。

M4 で interleave の効果が 4.3% しかなかったのは、コアの速さの違いよりも、worker がコアを移動していたことが効いていた、というのが今回の結論（M4 実機での確認はまだ）。詳しくは docs/hetero-experiments.md。

一次資料

遅いコアの作り方は Linux カーネルの CFS Bandwidth Control。M4 の P/E コアのクロックは Oakley の測定 Inside M4 chips: E and P cores。
