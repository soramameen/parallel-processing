# 非対称コア下の極大クリーク列挙 — 研究計画

作成: 2026-09-22

## 問い

コア速度が不揃いな環境で、Eppstein 法の外側ループ（とその内部）をどう配れば makespan が最小になるか。

卒論（`thesis/chapters/05-experiments.tex`）で得たのは「均等に配っても速くならない」という負の結果までだった。
M4 では interleave が idle を 32.6% → 0.1% に消したのに compute は 4.3% しか縮まず、原因は P/E 非対称コアだった。
本計画はこれを、速度差を前提とした配分方式の提案と定量評価に変える。

**中心仮説**: 動的な配分ほど、コア速度 r を知らなくても非対称性に自動適応する。
静的配分は r を知る必要があるが、macOS では r を正確に測れない（0.26 は下限実測、0.43 は推定）。
これが動的方式を推す論拠になる。

## 進め方の骨子

1. **(b) 人工的な非対称環境を作る**: Linux で「真の r が既知」の遅いコアを作り、M4 の現象を再現する
2. **(a) シミュレータ**: 頂点ごとの実測コストとコア速度から makespan を計算し、実測との誤差を検証する
3. 配分方式を提案・実装し、r を振って比較する
4. M4 実機で傾向を確認する
5. 論文化

「制御された環境で原理を示す → 実機で現実性を確かめる」の二段構え。

## Phase 1: 非対称コアのエミュレーション・ハーネス（推奨の (b)）

### 1-1. 実装: `src/parallel_processing/hetero.py`

- コアごとに cgroup `/sys/fs/cgroup/cpu/pp_core{i}` を作り、`cpu.cfs_quota_us = r_i × period` を設定する
- worker を 1 コアに 1 個固定する
  - Pool の initializer に `multiprocessing.Queue` でスロット番号を配る
  - 各 worker は `os.sched_setaffinity(0, {cpu_i})` を呼び、自分の pid を `pp_core{i}/cgroup.procs` に書く
- `_count_batch_timed` の戻り値に slot（コア種別）を加え、busy をコア種別ごとに集計する
- コア構成は文字列で指定する。例: `--cores F,F,S,S --r 0.43`
- 終了時に cgroup を片付ける（`rmdir`）。異常終了にも備えて `try/finally` で囲む
- cgroup が使えない環境（macOS、非 root）ではエラーメッセージを出して終了する（テストは skip）

**period の選択**: 既定の 100ms だと「43ms 走って 57ms 止まる」という粗い stop-and-go になり、短いタスクの計測を歪める。
10ms を基本にし、1ms / 10ms / 100ms で純ループの実効 r がどう変わるかを最初に較正する。

### 1-2. 較正実験

- 純計算ループと、soc の代表頂点（重・中・軽の 3 個）のサブ問題の両方について、設定 r ∈ {1, 0.75, 0.5, 0.43, 0.26} での実効 r を測る
- 設定値と実効値のずれを表にする。以後の理論値にはこの実効値を使う

### 1-3. 再現実験（最初の検証点）

問い: M4 で見た「idle は消えたのに速くならない」現象が、真の r が既知の環境で再現するか。

| 構成 | 意味 |
|---|---|
| `F×1` | 基準（F コア 1 個分のスループット） |
| `S×1` | r の実測 |
| `F×4` | 均質 4 コア。idle が消えれば素直に速くなるはず |
| `F×2 + S×2` | 非対称。M4 の縮図 |
| `S×4` | 遅いコアのみ |

- 配分方式: block / interleave / 細粒度動的（バッチ 64・16・4・1）
- r ∈ {0.75, 0.43, 0.26}
- グラフ: ca-AstroPh、ca-HepPh（短時間で回る）、soc-sign-epinions（主役、ただし重い）
- 各条件 3 回の最小値。条件の実行順は交互にする（既存の計測プロトコルを踏襲）
- 各 run の前後で `/proc/stat` の steal 時間を記録し、クラウドの隣人ノイズを監視する

**指標**:
- **理想スループット** = n_F + n_S × r（F コア換算）
- **達成スループット** = T(F×1) ÷ T(構成)
- **効率** = 達成 ÷ 理想
- **idle%**: 従来の定義と、速度で重み付けした定義の両方
- コア種別ごとの busy と処理頂点数

**期待される結果**: `F×4` では idle の消滅がそのまま高速化になり、`F×2+S×2` ではならない。
これが出れば、「idle% は均質コアを仮定した指標である」という卒論の主張を、制御された実験で裏づけられる。

## Phase 2: シミュレータ（推奨の (a)）

### 2-1. 実装: `src/parallel_processing/sched_sim.py`

- 入力は、頂点ごとのコスト（`workload_profile.py` の CSV）、コア速度のリスト、配分方式
- 離散イベントシミュレーションで makespan、コアごとの busy、idle を出す
- 配分方式: block、reversed、interleave、動的バッチ k、速度重み付き LPT（コストは実測値または |P| による予測）、理想的な work stealing（下限）
- **下限**を併記する: max(Σコスト ÷ Σ速度, 最重タスク ÷ 最速コア)

### 2-2. 検証

- このクラウド環境で `workload_profile.py` を回し直す（CSV は M4 で測ったものなので、Linux 用に取り直す）
- Phase 1 の実測とシミュの makespan を比べ、誤差 ±10% 以内を目標にする
- ずれた条件では原因を特定する（共有資源の競合、ディスパッチのオーバーヘッド、stop-and-go の粒度など）

### 2-3. 使い道

- r とコア構成を連続的に振り、方式の優劣が入れ替わる境界を地図にする（実測では回しきれない範囲をシミュで埋める）
- 余裕があれば `assets/scheduler.js` を P/E 対応にし、レッスン 0004 にする（学習用）

## Phase 3: 配分方式の提案と比較

1. **速度重み付き LPT（静的）**: |P| で仕事量を予測し、コア速度 r に比例して割り当てる。r の誤差（0.26 と 0.43 の取り違え）への感度も測る
2. **細粒度動的**: 共有キューとバッチ縮小。ディスパッチのオーバーヘッドとの損益分岐を求める
3. **work stealing と部分問題の分割**: 探索木の途中で P 集合を切り出してキューに戻す。ca-HepPh 型（1 頂点が全体の 13%）の救済に必要
   - 遅いコアから優先して盗む「weaker first」原則の効果も確かめる
4. **遅いコアの後半停止**: 終盤の重いタスクを遅いコアに渡さない（尾の処理）

各方式を Phase 1 のハーネスとシミュで評価し、r の知識の要否、r への頑健さ、実装の複雑さを比較表にまとめる。

## 妥当性への脅威（先に書いておく）

- **cgroup の quota は DVFS と違う**: quota はプロセスを間欠停止させる方式で、クロックは下がらない
  - 実機の低クロックではメモリ待ちが相対的に軽くなる（卒論 5 章: 純ループ 5.75 倍、soc 3.79 倍）が、quota では計算もメモリ待ちも同じ比率で遅くなる
  - したがって、エミュレーションの r は「ワークロード非依存の一様な減速」のモデルである
- **KVM の vCPU ノイズ**: 隣人の影響を受ける。steal 時間を記録し、異常な run は除外基準を事前に決めておく
- **4 vCPU しかない**: 構成は最大 4 worker。より多いコアの挙動はシミュで補う
- **L3 共有**: 全コアで L3 を共有するため、競合ロスは M4 と性質が異なる可能性がある
