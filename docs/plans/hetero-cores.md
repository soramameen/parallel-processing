# 非対称コア下の極大クリーク列挙 — 研究計画

作成: 2026-09-22 / 改訂: 2026-09-23（スコープを Linux クラウド環境のみに限定）

## 問い

コア速度が不揃いな環境で、Eppstein 法の外側ループ（とその内部）をどう配れば makespan が最小になるか。

卒論（`thesis/chapters/05-experiments.tex`）で得たのは「均等に配っても速くならない」という負の結果までだった。
M4 では interleave が idle を 32.6% → 0.1% に消したのに compute は 4.3% しか縮まず、原因は P/E 非対称コアだった。
本計画はこれを、速度差を前提とした配分方式の提案と定量評価に変える。

**中心仮説**: 動的な配分ほど、コア速度比 r（遅いコアの速さ ÷ 速いコアの速さ）を知らなくても非対称性に自動適応する。
静的配分は r を知る必要があるが、現実の r は条件によって動き、正確には測れない。
これが動的方式を推す論拠になる。

## スコープ

**今回の範囲**: この Linux クラウド環境（Claude Code on the web）だけで完結するもの。

- cgroup による「r が既知の遅いコア」のエミュレーション実験
- 実測コストを入力にしたシミュレータ
- 配分方式の実装と比較

**範囲外**（Mac が使えないため）: M4 実機での r の確定（powermetrics）、M4 での追試。
したがって本研究の結論は「r がある範囲にある非対称環境で、どの方式が有利か」という**条件付きの主張**であり、M4 について直接何かを実証するものではない。
M4 との対応は、r の範囲の選び方の根拠（下記）として使うにとどめる。

## r の範囲の根拠（外部情報からの推定、本研究では検証しない）

M4 でクリーク列挙を並列実行したとき、E コアの速さは P コアの **r ≈ 0.4〜0.5** 倍と推定する。
卒論の 0.26 は、background QoS でクロックが約 1.05GHz に張り付いた条件での下限値である。

| # | 仮説 | 裏付け | 地位 |
|---|---|---|---|
| H1 | 速さの差の大部分はクロック差である | E コア固定時は約 1.05GHz、全力なら 2.59GHz（Oakley）。1.02GHz の E コア 4 個と約 4GHz の P コア 4 個で 4.3 倍差（M4 Pro） | 第三者の測定 |
| H2 | 残りは IPC 差（約 1.37 倍）で、ほぼ一定 | 純計算ループ 5.75 倍 ÷ クロック比 4.2 倍 | 自前の測定からの推定 |
| H3 | 速いコアを全部使うと速いコアのクロックが下がり、並列時は差が縮む | P は単独で 4.5GHz、4 個とも忙しいと約 4GHz。P のみの w=4 の効率は 79% | 第三者の測定＋自前の測定 |
| H4 | メモリ待ちがあるため、クロック差ほどには遅くならない | E コア固定で純ループ 5.75 倍、soc 3.79 倍 | 自前の測定 |

計算上の値は、単独実行で 2.59/4.4/1.37 ≈ 0.43、並列実行で 2.59/4.0/1.37 ≈ 0.47。

**計画への帰結**:

1. r は **0.26〜0.75 の範囲で振り**、0.43〜0.5 を本命の帯とする
2. r は定数ではない（H3: 忙しいコアの数で変わる、H4: タスクで変わる）。静的配分に入れる r はいつも少しずれるので、**r を見誤ったときの損**を主要な評価軸にする
3. この環境で再現できるのは H1〜H3 まで。H4 はシミュレータだけで扱う（下表）

| 現象 | この環境での扱い | 手段 |
|---|---|---|
| 一様な減速（H1〜H2） | 実測で再現 | cgroup の `cpu.cfs_quota_us` |
| 忙しいコア数で速さが変わる（H3） | 実測で再現 | 親プロセスの制御スレッドが、実行中に quota を書き換える |
| タスクで r が変わる（H4） | シミュのみ | quota は計算もメモリ待ちも同率で遅くするため、実測では作れない |

## Phase 1: 非対称コアのエミュレーション・ハーネス

### 1-1. 実装: `src/parallel_processing/hetero.py`

- コアごとに cgroup `/sys/fs/cgroup/cpu/pp_core{i}` を作り、`cpu.cfs_quota_us = r_i × period` を設定する
- worker を 1 コアに 1 個固定する
  - Pool の initializer に `multiprocessing.Queue` でスロット番号を配る
  - 各 worker は `os.sched_setaffinity(0, {cpu_i})` を呼び、自分の pid を `pp_core{i}/cgroup.procs` に書く
- `_count_batch_timed` の戻り値に slot を加え、busy と処理頂点数をコア種別ごとに集計する
- コア構成は文字列で指定する。例: `--cores F,F,S,S --r 0.43`
- **速さを動的に変えるモード**（H3 用）: 親プロセスの制御スレッドが、忙しい F コアの数に応じて F の quota を書き換える（例: 4 個とも忙しいとき 0.79）
- 終了時に cgroup を片付ける（`rmdir`）。異常終了にも備えて `try/finally` で囲む
- cgroup が使えない環境ではエラーメッセージを出して終了する（テストは skip）

**period の選択**: 既定の 100ms だと「43ms 走って 57ms 止まる」という粗い stop-and-go になり、短いタスクの計測を歪める。
4ms / 10ms / 100ms で較正し、実効 r が安定する最短の period を採る（10ms を想定）。
カーネルは 1ms 未満の quota を受け付けないため、速さ s を表せる period は 1ms ÷ s 以上に限られる（s = 0.26 なら 3.85ms 以上）。

### 1-2. 較正実験

- 純計算ループと、soc の代表頂点（重・中・軽の 3 個）のサブ問題について、設定 r ∈ {1, 0.75, 0.5, 0.43, 0.26} での実効 r を測る
- quota ではメモリ待ちも同じ比率で遅くなるので、頂点によらず実効 r がほぼ一定になるはず。これを確かめること自体が、「エミュレーションの r はワークロードに依存しない」という前提の確認になる
- 設定値と実効値のずれを表にする。以後の理論値には実効値を使う

### 1-3. 再現実験（最初の検証点）

問い: M4 で見た「idle は消えたのに速くならない」現象が、真の r が既知の環境で再現するか。

| 構成 | 意味 |
|---|---|
| `F×1` | 基準（F コア 1 個分のスループット） |
| `S×1` | r の実測 |
| `F×4` | 均質 4 コア。idle が消えれば素直に速くなるはず |
| `F×2 + S×2` | 非対称。M4 の縮図 |
| `F×1 + S×3` | 遅いコアが多数派の場合 |
| `S×4` | 遅いコアのみ |

- 配分方式: block / interleave / 細粒度動的（バッチ 64・16・4・1）
- r ∈ {0.75, 0.5, 0.43, 0.26}
- グラフ: ca-AstroPh、ca-HepPh（短時間で回る）、soc-sign-epinions（主役、ただし重い）
  - soc は 1 run あたり数分かかる見込み。全条件を回しきれない場合は soc を主要条件だけに絞り、残りはシミュで補う
- 各条件 3 回の最小値。条件の実行順は交互にする（既存の計測プロトコルを踏襲）
- 各 run の前後で `/proc/stat` の steal 時間を記録する。除外基準（例: steal が 1% を超えた run は除外）は測定前に決める

**指標**:
- **理想スループット** = n_F + n_S × r（F コア換算）
- **達成スループット** = T(F×1) ÷ T(構成)
- **効率** = 達成 ÷ 理想
- **idle%**: 従来の定義と、速度で重み付けした定義の両方
- コア種別ごとの busy と処理頂点数

**期待される結果**: `F×4` では idle の消滅がそのまま高速化になり、`F×2+S×2` ではならない。
これが出れば、「idle% は均質コアを仮定した指標である」という卒論の主張を、真値が既知の条件で裏づけられる。

## Phase 2: シミュレータ

### 2-1. 実装: `src/parallel_processing/sched_sim.py`

- 入力は、頂点ごとのコスト（`workload_profile.py` の CSV）、コア速度のリスト、配分方式
- 離散イベントシミュレーションで makespan、コアごとの busy、idle を出す
- 配分方式: block、reversed、interleave、動的バッチ k、速度重み付き LPT（コストは実測値または |P| による予測）、理想的な work stealing（下限）
- **下限**を併記する: max(Σコスト ÷ Σ速度, 最重タスク ÷ 最速コア)
- r を定数にしないモデルも入れる
  - H3: 忙しい F コアの数に応じて F の速さを下げる。Phase 1 の動的モードと同じ規則にし、実測と突き合わせる
  - H4: タスクごとに r を変える。実測の根拠がないので、分布の形（一様、重い頂点ほど r が高い、など）を複数置いて感度を見る
  - これらを入れたときと入れないときで、方式の順位が入れ替わるかを見る

### 2-2. 検証

- この環境で `workload_profile.py` を回し直す（既存の CSV は M4 で測ったものなので、Linux 用に取り直す）
- Phase 1 の実測とシミュの makespan を比べ、誤差 ±10% 以内を目標にする
- ずれた条件では原因を特定する（共有資源の競合、ディスパッチのオーバーヘッド、stop-and-go の粒度など）

### 2-3. 使い道

- r とコア構成を連続的に振り、方式の優劣が入れ替わる境界を地図にする
- 4 vCPU を超える構成（例: M4 と同じ 4F+6S）はシミュでのみ扱う
- 余裕があれば `assets/scheduler.js` を P/E 対応にし、レッスン 0004 にする（学習用）

## Phase 3: 配分方式の提案と比較

1. **速度重み付き LPT（静的）**: |P| で仕事量を予測し、コア速度 r に比例して割り当てる
2. **細粒度動的**: 共有キューとバッチ縮小。ディスパッチのオーバーヘッドとの損益分岐を求める
3. **work stealing と部分問題の分割**: 探索木の途中で P 集合を切り出してキューに戻す。ca-HepPh 型（1 頂点が全体の 13%）の救済に必要
   - 遅いコアから優先して盗む「weaker first」原則の効果も確かめる
4. **遅いコアの後半停止**: 終盤の重いタスクを遅いコアに渡さない（尾の処理）

各方式を Phase 1 のハーネス（4 worker まで）とシミュ（それ以上）で評価し、r の知識の要否、r への頑健さ、実装の複雑さを比較表にまとめる。

**r の見積もり誤差への頑健さ（主要な評価軸）**: 静的方式に入れる r を、真の r からずらして与える。
例えば真の r = 0.45 に対して 0.26、0.43、0.6 を与え、makespan の悪化率を測る。
動的方式は r を使わないので、悪化率は 0 が基準になる。
H3 の動的モード（実行中に r が動く）でも同じ比較をする。
動的方式と work stealing の評価では、period を 4ms / 10ms で振り、quota で止まっている間の応答遅れが順位を変えないかを確認する（妥当性への脅威を参照）。
「r を正しく知っていれば静的方式が勝つが、少しずれると動的方式に負ける」という境界が見つかれば、それが論文の中心となる図になる。

## 妥当性への脅威

- **cgroup の quota は DVFS と違う**: quota はプロセスを間欠停止させる方式で、クロックは下がらない
  - 実機の低クロックではメモリ待ちが相対的に軽くなる（H4）が、quota では計算もメモリ待ちも同じ比率で遅くなる
  - したがって、エミュレーションの r は「ワークロード非依存の一様な減速」のモデルである
- **quota の粒度**: period 内で走る→止まるを繰り返すため、タスクが短いと実効 r がぶれる。1-2 の較正で確認する
- **止まっている間は応答しない**: 低クロックのコアは遅くてもすぐ反応するが、quota で止められたコアは最大 (1−r)×period の間まったく反応しない
  - 細粒度動的や work stealing では、仕事の受け渡しに余計な待ちが入り、**動的方式が実機より不利に見える**おそれがある
  - 中心仮説とは逆向きの歪みなので、動的方式が勝った場合の結論は保守的に扱ってよいが、負けた場合はこの影響を切り分ける（period を変えて結果が動くかを見る）
- **busy は経過時間で測る**: `perf_counter` には止まっていた時間も含まれ、遅さが正しく見える。`process_time` には入らないので使わない
- **KVM の vCPU ノイズ**: 隣人の影響を受ける。steal 時間を記録し、事前に決めた基準で除外する
- **4 vCPU しかない**: 実測は最大 4 worker。より多いコアの挙動はシミュで補い、その部分はシミュの結果であると明記する
- **L3 共有**: 全コアで L3 を共有するため、競合ロスは M4 と性質が異なる可能性がある
- **M4 との対応は未検証**: r の範囲は外部情報からの推定で、本研究では確かめない
