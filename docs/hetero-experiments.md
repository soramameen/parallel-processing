# 非対称コア下の Eppstein 並列化 — エミュレーション実験の記録

2026-09-22 から 09-23 にかけて、速さの違うコアが混在する環境で極大クリーク列挙（Eppstein 法）をどう配るべきかを、Linux 上のエミュレーションとシミュレーションで調べた。
この資料はその結果を、経緯を含めて記録する。
計画は `docs/plans/hetero-cores.md`、M4 での前段の実験は `docs/eppstein-experiments.md` と卒論 5 章にある。

実行環境はすべて同一（Claude Code on the web のクラウド環境、KVM 上の Intel Xeon 2.80GHz 4 vCPU、SMT なし、純 Python 3.12.3、spawn 方式の multiprocessing）である。
M4 実機は使えなかったため、本資料の主張は「コアの速さの比 r がある範囲にある非対称環境で何が起きるか」という条件付きのものであり、M4 について直接実証したものではない。

## 要点

1. **遅いコアは作れる。** cgroup の CPU 時間制限で作った遅いコアは、クリーク列挙のタスクで設定した速さの 0.92〜0.98 倍で走り、タスクの種類による差は 5% 以内だった
2. **コアを固定すると、M4 の現象は再現しない。** interleave は 8 通りのコア構成すべてで理想スループットの 93〜98% に達し、block より 1.04〜1.76 倍速かった。busy 合計の膨張も起きなかった
3. **M4 の現象は、OS が worker をコア間で移すことで説明できる（H5）。** M4 のコストでシミュレーションすると、移動ありなら M4 の block と reversed の実測に近づき、固定では説明できない。エミュレーションでも、移動を入れると block は 18〜53% 速くなり、interleave は変わらず、busy 合計の向きも M4 と一致した
4. **idle% は「worker = コア」を仮定した指標である。** 卒論の「コアが均質であることを仮定した指標」という結論を、この形に言い直す
5. **r もコストも使わない配り方が、最速の群に入る。** 実測では interleave、1 頂点ずつの block、予測コスト順の lpt、実測コスト順の lpt が 75.0〜75.4 秒で並んだ。シミュレーションでも M4 の形で interleave は下限の 1.00〜1.07 倍だった
6. **r を使う静的配分はもろい。** 正しい r と実測コストを与えても実測で 4% 負けた（実行中の r は 0.39〜0.41 で、設定値 0.43 より 5〜10%、1 コアで較正した 0.42 より 2〜7% 低かった）。r を取り違えると 11〜30%、非対称を無視すると 72% 遅くなり、r が実行中に変わる（H3）と 3〜7% 負けた
7. **遅いコアも使うべきかは、配り方で決まる。** 偏りをならせる配り方なら全コアを使う方が速い（M4 の形で 4 worker の 49.4 秒から 10 worker の 30.1 秒）。block では worker を増やすと遅くなることもある
8. **ca-HepPh の重い頂点は分割できないが、早期終了で 19 倍速くなる。** 全仕事の 13% を占める頂点の探索木は枝分かれのない一本道だった。候補集合がクリークなら直接答える早期終了を実装すると、逐次で ca-HepPh が 1.24 倍、ca-AstroPh が 1.08 倍速くなり、ca-HepPh の最重の頂点は全仕事の 0.85% まで下がった（判定を根だけで行えば、該当する頂点のない soc-sign-epinions でも損はなかった）。シミュレーションでは、ca-HepPh の並列の上限（7.48 倍）が消え、32 コアで 31.8 倍まで伸びる


## 背景と問い

卒論の実験では、M4（P コア 4 + E コア 6）で interleave 配分が worker の遊休を 32.6% から 0.1% に消したのに、計算時間は 4.3% しか縮まなかった。
卒論はこの原因を P/E コアの速さの違いに求め、「idle% はコアが均質であることを暗に仮定した指標である」と結論した。
ただし macOS では、プロセスを P コアに固定することも、E コアを既知の速さで動かすこともできないため、この説明は推測の域を出なかった。

本実験の問いは二つある。

1. コアの速さの比 r が分かっている環境で、M4 の現象は再現するか
2. 速さの違うコアに対して、どの配り方が最も速く、r を見誤ったときにどれだけ損をするか

## 実験環境と方法

### 遅いコアの作り方

各 worker を 1 個の CPU に固定し（`os.sched_setaffinity`）、worker ごとに cgroup v1 の `cpu` グループを作って CPU 時間の上限（`cpu.cfs_quota_us`）をかけた。
上限を周期の r 倍にすると、そのコアは「周期のうち r の割合だけ全速で走り、残りは止まる」ので、長い時間で見れば速さ r のコアになる。
速さ 1 のコアも上限なしのグループに入れ、全 worker が同じ経路を通るようにした。
実装は `src/parallel_processing/hetero.py`、CLI は `benchmark_hetero.py` と `hetero_phase3.py` である。

この方法はクロックを下げるのとは違う。
止まっている間はメモリ待ちも含めて全部が止まるので、エミュレーションの r は「どの処理も同じ割合で遅くなるコア」のモデルになる（実機の低クロックではメモリ待ちは伸びない）。
また、止まっている間のコアは新しい仕事を受け取れない。
これらの限定は「妥当性への脅威」の節にまとめた。

### 実行器

二種類の実行器を使った。

- **Pool 実行器**（`profile_hetero`）: M4 の実験と同じ `multiprocessing.Pool` と `imap_unordered` で、バッチを共有キューから順に取る。Phase 1 の再現実験に使った
- **pull 実行器**（`profile_pull`）: 各 worker が共有メモリ上のカーソルを進めて、自分に許されたキューから直接仕事を取る。コアごとの静的リスト、共有キュー、速いコア専用キュー、部分問題の分割を同じ仕組みで表せる。Phase 3 の比較に使った

pull 実行器には二つの制御モードがある。

- **速さの変動（H3）**: 親プロセスの制御スレッドが、働いている速いコアの数に応じて速いコアの上限を書き換える
- **worker の移動（H5）**: 仕事が尽きた worker が速いコアを空けると、遅いコアで働いている worker に速いコアの役を引き継がせる（その worker の上限を外す）。macOS が空いた P コアへ E コアのスレッドを移す振る舞いの模倣である

### 測定の手順

- 各条件 3 回（Phase 3 の一部は 2 回または 5 回）走らせて最小値を採用する。条件の実行順は 1 回ごとに一巡させ、ホストの遅い時間帯がすべての条件に等しく乗るようにした
- 各 run の前後で `/proc/stat` の steal 時間（ハイパーバイザに奪われた時間）を記録した。除外基準は測定前に「steal が (コア数 × compute) の 3% を超えた run は除外」と決めた
- 極大クリーク数はすべての run で 22,226,173（soc-sign-epinions）に一致することを assert している
- 測定中に自分の解析処理を走らせるときは `nice -n 19` で最低優先度にした

## 較正: 遅いコアは設定どおりの速さで走るか

1 個のコアに速さ s を設定し、4 種類のタスクで実効速度（全速の時間 ÷ 速さ s での時間、3 回の最小値）を測った。
タスクは純 Python の整数ループと、soc の外側ループから切り出した 3 種類（最も |P| の大きい 1 頂点、中くらいの頂点 2,000 個、軽い頂点 12 万個）である。

| 周期 | タスク | s=0.75 | s=0.5 | s=0.43 | s=0.26 |
|---|---|---|---|---|---|
| 4 ms | 整数ループ | 0.786 | 0.523 | 0.446 | 0.267 |
| 4 ms | 重い 1 頂点 | 0.748 | 0.493 | 0.420 | 0.244 |
| 4 ms | 中くらい | 0.743 | 0.488 | 0.420 | 0.242 |
| 4 ms | 軽い | 0.743 | 0.502 | 0.417 | 0.241 |
| 10 ms | 整数ループ | 0.753 | 0.498 | 0.429 | 0.255 |
| 10 ms | 重い 1 頂点 | 0.742 | 0.480 | 0.416 | 0.246 |
| 10 ms | 中くらい | 0.742 | 0.478 | 0.408 | 0.241 |
| 10 ms | 軽い | 0.729 | 0.468 | 0.397 | 0.235 |
| 100 ms | 整数ループ | 0.783 | 0.534 | 0.449 | 0.271 |
| 100 ms | 重い 1 頂点 | 0.755 | 0.502 | 0.442 | 0.258 |
| 100 ms | 中くらい | 0.766 | 0.494 | 0.431 | 0.257 |
| 100 ms | 軽い | 0.741 | 0.489 | 0.415 | 0.250 |

実効速度は設定値の 0.92〜1.05 倍に収まった。
クリーク列挙のタスクは設定値よりわずかに遅く（0.92〜0.98 倍）、タスクの種類による差は最大 5% だった。
エミュレーションの r がワークロードにほとんど依存しないという前提は、これで確かめられた。

周期は **4 ms** を採用した。
4 ms は 100 ms と同じくらい設定値に近く（クリーク列挙で 0.97〜0.98 倍）、止まっている時間が最も短い（r = 0.26 でも 3 ms 未満）。
10 ms はなぜかわずかに悪かった。
カーネルは 1 ms 未満の上限を受け付けないので、速さ s を表せる周期は 1 ms ÷ s 以上に限られる（s = 0.26 なら 3.85 ms 以上）。
実装は、短すぎる周期を黙って全速にせず、エラーにする。

以降の「理想スループット」には、この表の重い 1 頂点と中くらいの平均を r の実効値として使う（4 ms で r=0.43 → 0.420、r=0.26 → 0.243、r=0.75 → 0.745）。

## 逐次ベースラインと負荷分布

| 項目 | この環境 | M4（卒論） |
|---|---|---|
| soc の Eppstein 逐次（3 回） | 202.6 / 202.9 / 203.9 秒 | 94.9 秒 |
| Pool 実行器の F×1（3 回の最小値） | 198.8 秒 | 96.0 秒 |
| 上位 0.1% の頂点が占める時間 | 45.0% | 45.2% |
| 上位 1% の頂点が占める時間 | 94.5% | 94.7% |
| 最重の 1 頂点 | 0.88% | 0.86% |

この環境は M4 の約 2.1 倍遅いが、負荷の偏りの形は M4 とほぼ同じだった。
重い頂点が縮退順序の末尾に固まるという性質はグラフ由来であり、マシンに依存しない。

|P|（候補集合の大きさ）は仕事量の予測子として中程度だった。
順位相関（Spearman）は 0.86 で、|P| の上位 1% は全時間の 65% しか占めない（本当の上位 1% は 94.5%）。
Phase 3 では、log(時間) = a + b|P| を同じグラフでフィットした予測値を「予測コスト」として使った（b = 0.095、|P| が 1 増えるごとに約 1.10 倍）。
同じグラフでフィットしているので、実際の用途より楽観的な予測子である。

## 再現実験（Phase 1）: コアを固定すれば idle を消した分だけ速くなる

### 意図

M4 の「idle を消しても速くならない」現象が、真の r が分かっている環境でも起きるかを確かめる。
起きるなら、原因はコアの速さの違いそのものにある。
起きないなら、M4 には速さの違い以外の何かがあったことになる。

### 方法

soc-sign-epinions、バッチ 64、Pool 実行器（M4 と同じ `imap_unordered`）、周期 4 ms、各条件 3 回の最小値である。
コア構成は、速いコア（F）と遅いコア（S）の組み合わせ 5 通りと、遅いコアの速さ r 3 通りで、合計 17 条件を 3 巡した（約 93 分）。
スループットは F×1 の compute（198.8 秒）を当該条件の compute で割った値で、「速いコア何個分の仕事が出たか」を表す。
理想は（速いコア数 + 遅いコア数 × r の実効値）で、効率はスループット ÷ 理想である。

### M4 の現象は、コアを固定すると再現しない

interleave は全 8 構成で idle を 1% 前後まで消し、理想スループットの 93〜98% に達した。
idle を消した分はそのまま速さになり、interleave は block より 1.04〜1.76 倍速かった。
busy 合計（worker が働いた時間の和）は、block と interleave でほとんど変わらないか、interleave の方が少なかった（F,F,S,S r=0.43 で 293 秒対 286 秒）。
M4 で見た「idle が消えると busy が 139 秒から 198 秒に膨らむ」現象は、どの構成でも起きなかった。

つまり、コアの速さが違うこと自体は、idle% を無意味にしない。
worker がずっと同じコアで働くなら、「理想 = 速いコア数 + 遅いコア数 × r」という単純なモデルが 93〜98% の精度で成り立ち、idle を消すことはそのまま高速化になる。
M4 には、コアの速さの違い以外に何かがあった。
その候補が次々節の worker の移動（H5）である。

### block の遅さは、遅いコアの数と r で決まる

block の効率は 56〜92% とばらついた。
最も悪いのは F,F,S,S r=0.26 の 56% で、重い末尾のバッチが遅いコアに乗り、速いコアが早く終わって待つ形になった（busy は速いコア 2 個が 61 秒と 84 秒、遅いコアが 98 秒と 143 秒）。
遅いコアが多い F,S,S,S や S,S,S,S では、もともと遅いコアで全体が律速されるので、block の損は相対的に小さい。

### block は遅いだけでなく、予測できない

3 回の max/min は、block が 1.06〜1.42、interleave がほぼ 1.01〜1.10 だった（F,F,F,F の 1.15 は 1 回だけ遅い run があったため）。
block では重い末尾のバッチが最後に配られるので、どのコアがそれを引くかがわずかな時間差で決まる。
遅いコアが引けば遅く、速いコアが引けば速い。
次節のシミュレータでも、バッチのコストに ±5% の揺らぎを入れるだけで block の完了時間は大きく散った。
非対称なコアでは、block の性能はくじ引きに近い。


## シミュレータの検証

### 方法

`sched_sim.py` は、頂点ごとの実測コスト（`artifacts/linux/workload-soc-sign-epinions.csv`）とコアの速さから、共有キューを貪欲に取る配分の完了時間を計算する。
Phase 1 の各条件を、較正した r の実効値で再現した。
「競合あり」は、4 コアが同時に働くときの 1 コアあたりの速さ（F,F,F,F interleave から求めた 0.978）を全コアに掛けたものである。
block については、バッチのコストに σ = 0.05 の対数正規の揺らぎを入れて 40 回回し、10〜90 パーセンタイルの幅も求めた。

interleave は、競合ありのシミュで 7 構成中 6 構成が ±2.4% に収まった（遅いコアだけの S,S,S,S は -5.3%）。
シミュレータは、偏りの少ない配分の完了時間をよく予測する。

block の揺らぎなしの誤差は最大 +28% と大きいが、これはシミュレータの欠陥というより block の性質である。
揺らぎを入れると block の完了時間は ±10〜25% の幅で散り、実測（3 回の最小値）はその幅の下端付近か、それより下に入る。
3 回の最小値を採る手順は、block については「3 回のうち最も運のよいくじ」を選んでいることになる。
以降、シミュレータは interleave や細かい動的配分の比較には使い、block の絶対値の予測には使わない。


## M4 の謎を見直す: worker の移動（H5）

### 仮説

macOS はプロセスをコアに固定しない。
仕事の尽きた worker が P コアを空けると、スケジューラは E コアで待っている実行可能なスレッドをその P コアへ移す。
block では worker が 1 人ずつ早く終わるので、末尾の重いバッチを抱えた worker は、終盤に P コアへ移って速く走れる。
すると block の「worker の idle」は、速いコアが遊んでいた時間ではない。
それを interleave で消しても、速いコアの仕事は増えず、E コアで最後まで粘る worker が増えるだけになる。
M4 で interleave にすると busy 合計が 139 秒から 198 秒に膨らんだのは、E コアで働く時間が増えたためだと考えられる。

### シミュレータで M4 の実測を再現する

シミュレータに移動を入れた（`sched_sim.simulate(migrate=True)`）。
worker とコアを分け、worker は速いコアから順に置く。
仕事の尽きた worker がコアを空けると、いちばん遅いコアで働いている worker が、途中の仕事ごとそこへ移る。
M4 の頂点ごとのコスト（`artifacts/workload-soc-sign-epinions.csv`、P コアで計 98.0 秒）で、M4 の構成（P 4 + E 6、w=8）を再現した。
M4 の実測は卒論の配分戦略比較のセッション（Chrome を開いていた回）の値である。

![M4 の w=8 を再現](figures/hetero-m4-replay.svg)

| w | 戦略 | r | 固定（シミュ） | busy | 移動あり（シミュ） | busy | M4 実測 | busy |
|---|---|---|---|---|---|---|---|---|
| 8 | block | 0.26 | 69.6 s | 275 s | 25.7 s | 125 s | 25.9 s | 139 s |
| 8 | block | 0.43 | 33.9 s | 150 s | 21.1 s | 121 s | 25.9 s | 139 s |
| 8 | reversed | 0.26 | 67.3 s | 233 s | 26.0 s | 132 s | 28.5 s | 175 s |
| 8 | reversed | 0.43 | 40.7 s | 163 s | 23.8 s | 123 s | 28.5 s | 175 s |
| 8 | interleave | 0.26 | 20.4 s | 156 s | 19.6 s | 155 s | 24.7 s | 198 s |
| 8 | interleave | 0.43 | 17.6 s | 137 s | 17.3 s | 137 s | 24.7 s | 198 s |

固定のシミュレーションでは、block と reversed の M4 実測（25.9 秒、28.5 秒）はまったく説明できない（34〜70 秒になる）。
移動ありにすると、block は 21〜26 秒、reversed は 24〜26 秒になり、実測に近づく。
block と reversed の busy 合計も、固定の 150〜275 秒から、移動ありの 121〜132 秒に下がり、実測の 139〜175 秒の側に寄る。
M4 の block と reversed は、worker の移動があったと考えないと説明がつかない。

interleave では、移動の有無はほとんど効かない（全 worker が最後まで働くので、空く速いコアがない）。
シミュの 17〜20 秒に対してこのセッションの実測は 24.7 秒で、差は Chrome の負荷と共有資源の競合と考えられる（Chrome を閉じた再測定では 18.2 秒で、シミュの r = 0.35〜0.43 の範囲に入る）。
w=4 の実測（interleave 36.7 秒、busy 147 秒）も、4 worker がすべて P コアにいれば 24.5 秒のはずなので、このセッションでは P コアの一部が Chrome に取られ、worker が E コアに押し出されていたと読める。
w=4 の再現は、背景負荷を入れないこのシミュレータの範囲外である。

### 帰結: idle% は「worker = コア」を仮定した指標である

卒論は「idle% はコアが均質であることを暗に仮定した指標である」と結論した。
本実験の結果は、これをより正確に言い直す。

- コアの速さが違っても、worker がコアに固定されていれば、idle% はそのまま無駄な時間を表す（Phase 1）
- idle% が無駄を表さなくなるのは、worker がコアの間を移るときである。worker の idle と、速いコアの idle が一致しなくなる

スケジューリング理論の言葉で言えば、OS の移動は仕事を途中で別のコアへ移すことなので、非 preemptive な配分を preemptive（中断と移送あり）に近づける。
速さの違う機械の preemptive スケジューリングは最適解が効率よく求まる問題で（後述の下限の式）、移動が block の損を小さくするのはこのためである。

教材 `lessons/0004-fast-and-slow-cores.html` で、この違い（移動ありの block では worker の idle が大きいのに、速いコアの idle はほぼ 0 になる）を手で確かめられる。

### エミュレーションで確かめる（3e）

pull 実行器の移動モードで、同じ構成を「固定」と「移動あり」で 2 回ずつ測った（各 2 回の最小値）。

![worker を固定したときと移動させたとき](figures/hetero-migration.svg)

| r | 配り方 | 固定 | 移動あり | busy 合計（固定 → 移動あり） |
|---|---|---|---|---|
| 0.43 | block | 108.2 s | 88.9 s | 311 s → 283 s |
| 0.43 | reversed | 84.7 s | 79.6 s | 310 s → 292 s |
| 0.43 | interleave | 75.4 s | 75.5 s | 302 s → 302 s |
| 0.43 | lpt | 75.0 s | 74.7 s | 295 s → 297 s |
| 0.43 | static-oracle@0.43 | 77.9 s | 76.9 s | 304 s → 301 s |
| 0.26 | block | 211.4 s | 98.4 s | 464 s → 316 s |
| 0.26 | reversed | 161.3 s | 91.0 s | 406 s → 328 s |
| 0.26 | interleave | 85.9 s | 85.5 s | 341 s → 341 s |
| 0.26 | lpt | 94.3 s | 86.1 s | 346 s → 337 s |
| 0.26 | static-oracle@0.26 | 91.3 s | 85.4 s | 346 s → 337 s |

移動は、偏った配り方だけを大きく速くした。
block は r = 0.43 で 18%、r = 0.26 で 53% 速くなり、interleave はほとんど変わらなかった。
その結果、block と interleave の差は、固定の 1.43 倍（r = 0.43）・2.46 倍（r = 0.26）から、移動ありの 1.18 倍・1.15 倍に縮んだ。

busy 合計の向きも M4 と一致した。
固定では block の busy 合計が interleave 以上だった（311 秒対 302 秒、464 秒対 341 秒）のに、移動ありでは interleave の方が多くなった（283 秒対 302 秒、316 秒対 341 秒）。
M4 で見た「idle を消すと busy が膨らむ」は、移動があるときにだけ現れる。
移動ありの block では、先に仕事の尽きた worker の代わりに、遅いコアの worker が速いコアの役を引き継ぐので、同じ仕事を少ない busy で片付ける。
interleave は全員が最後まで働くので、遅いコアの worker は最後まで遅いままである。

以上で H5 は、エミュレーションとシミュレーションの両方で支持された。
M4 で interleave の効果が 4.3% しかなかったのは、コアの速さの違いそのものではなく、速さの違いと OS の移動の組み合わせによる、というのが本実験の結論である。
移動が block の損を先に大きく減らしていたので、interleave で減らせる分が小さかった。
ただし移動ありのシミュでも interleave は block より 20〜30% 速いはずで、実測の 4.3% との残りの差は、そのセッションの背景負荷（Chrome）が interleave の方に強く効いたためと考えられる（Chrome を閉じた interleave は 18.2 秒）。
M4 実機での確認は未実施である。



## 配分方式の比較（Phase 3）

### 方法

すべて pull 実行器で、soc-sign-epinions、F,F,S,S、周期 4 ms（3c を除く）である。
比べた配り方は次のとおり。

| 名前 | 中身 | 必要な知識 |
|---|---|---|
| block / block16 / block1 | 縮退順序を 64 / 16 / 1 頂点ずつ区切って順に配る | なし |
| reversed | block を末尾から配る | なし |
| interleave | 各バッチに頭と末尾の頂点を混ぜる（M4 の実験と同じ） | なし |
| lpt | 予測コスト（\|P\| から）の重い順に並べ、予測コストが上限に達するまで詰めたタスクを共有キューから取る | コストの予測 |
| lpt-oracle | lpt と同じだが、実測コストの順 | コストの実測 |
| static@R | 予測コストで速さ重み付きの静的 LPT。遅いコアの速さを R と仮定して、全頂点を最初に割り当てる | コストの予測と r |
| static-oracle@R | static@R の実測コスト版 | コストの実測と r |
| giants | lpt と同じだが、全仕事の 1/(8w) を超えると予測されたタスクは速いコアだけが（最初に）取る | コストの予測と、どれが速いコアか |
| split / split-giants | 同じく大きいと予測された頂点を第 1 層の枝に分けてから lpt / giants にする | コストの予測 |

スループットの基準は Phase 1 の F×1（Pool 実行器、198.8 秒）である。
pull 実行器は Pool 実行器より数%遅く（interleave で 75.1 秒対 72.2 秒）、効率はその分低く出るが、Phase 3 の中の比較には影響しない。

動的な 4 つ（lpt-oracle、interleave、block1、lpt）は 75.0〜75.4 秒で並び、互いの差は測定のばらつきの範囲だった。
r もコストも使わない interleave が、実測コストを使う lpt-oracle と同じ速さに達した。

静的配分は、正しい r（0.43）と実測コストを与えても、動的より 4% 遅かった。
r を 0.26 と取り違えると 11%、0.6 だと 30%、非対称を無視して 1.0 を入れると 72% 遅くなった。
シミュレータの予測（取り違えで 12〜22% の損、1.0 で 1.4〜1.6 倍）と同じ形である。

予測コストを使う static@0.43（76.2 秒）が、実測コストの static-oracle@0.43（78.2 秒）より速かったのは偶然に近い。
予測コストの誤差が、次に述べる r のずれを打ち消す方向に働いた。

### 実行中の r は、単独で測った r と違う

静的配分の各 run で、コアに割り当てた仕事量（実測コストの和）を、そのコアの busy 時間で割ると、実行中のコアの速さが分かる。

| 周期 | 速いコアの速さ | 遅いコアの速さ | 遅い ÷ 速い |
|---|---|---|---|
| 4 ms（13 run） | 0.92〜0.95 | 0.36〜0.39 | 0.39〜0.41 |
| 10 ms（2 run） | 0.93 | 0.38〜0.39 | 0.40〜0.41 |
| 100 ms（2 run） | 0.92 | 0.38〜0.39 | 0.41〜0.42 |

設定は 0.43、単独で較正した値は 0.42（4 ms）だったが、4 コアが同時に動く実行中の比は 0.39〜0.41 だった。
速いコアも 1 個で走るときの 0.92〜0.95 倍に落ちている（共有資源の競合）。
静的配分が「正しい r」でも 4% 負けたのは、このずれ（設定値から 5〜10%、単独の較正値から 2〜7%）のためである。
周期 100 ms では比が 0.41〜0.42 と設定に近く、静的配分の損も 1% 未満に縮んだ（3c）。

これは本研究の中心仮説の、実測による裏づけである。
r は、単独で丁寧に測っても、並列に動かすと変わる。
その値に頼る静的配分は、測り方の違いだけで数%を失い、r を 0.43 と 0.26 で取り違えると 1 割を失う。
動的な配り方は r を使わないので、この損がない。

### 3b: 速いコアが忙しいほど遅くなる場合（H3）

速いコアの速さを、2 個とも働いている間は 0.8、1 個だけなら 1.0 にした（親プロセスが実行中に上限を書き換える）。
このとき実行中の比は 0.43 ÷ 0.8 ≈ 0.53 になる。

| 配り方 | compute | 3 回の max/min |
|---|---|---|
| lpt | 88.9 s | 1.04 |
| interleave | 90.0 s | 1.01 |
| static-oracle@0.53（変動を見越した r） | 91.4 s | 1.02 |
| static-oracle@0.43 | 94.8 s | 1.02 |

動的な配り方が最速で、公称の r = 0.43 を使った静的配分は 7% 遅かった。
変動を見越して 0.53 を入れても 3% 遅い。
終盤に速いコアが 1 個だけ残ると比が変わるので、1 つの r では合わせきれない。

### 3c: 周期による違い

| 周期 | block | lpt | static-oracle@0.43 |
|---|---|---|---|
| 4 ms | 96.0 s | 75.4 s | 78.2 s |
| 10 ms | 95.0 s | 75.9 s | 77.3 s |
| 100 ms | 91.6 s | 76.7 s | 77.3 s |

周期を長くすると、動的な lpt はわずかに遅くなった（4 ms から 100 ms で +1.7%）。
止まっている間に仕事を取れない分の歪みで、予想どおり動的に不利な向きだが、大きさは 2% 未満である。
静的配分との差（4 ms で 3.7%、100 ms で 0.8%）が縮んだのは、主に実行中の r が設定に近づいたためである（前節の表）。

### 3d: ca-HepPh（1 頂点が 13% を占める）

ca-HepPh は 1 run が 0.5〜1 秒しかなく、同じ条件の 5 回の max/min が 1.06〜1.66 と大きかったので、配り方の差を結論できなかった（生データは `artifacts/linux/phase3.csv` の tag=3d）。
かわりに、分割がなぜ効かなかったかがはっきりした。

13% を占める頂点（候補集合 238 個）の第 1 層の枝は、**1 本しかなかった**。
候補集合 P の 238 頂点が互いに全部つながった 1 個のクリークなので、ピボットを選ぶと P から外れる頂点がピボット自身しか残らない。
探索木は深さ 238 の一本道で、枝で分けることはどの深さでもできない。
計画にあった「部分問題の内部分割（work stealing と分割）」は、この形の重い頂点には効かない。

一方、この頂点は分けなくても速くできる。
「P がクリークで、X のどの頂点も P の全体とつながっていなければ、答えは {v} ∪ P の 1 個だけ」と直接判定すると、174.7 ms が 9.0 ms（19 分の 1）になった。
P がクリークになる頂点が全仕事に占める割合は、ca-HepPh で 56.1%、ca-AstroPh で 18.0%、soc-sign-epinions で 0.1% だった。
共著グラフのように大きなクリークを含むグラフでは、並列化の工夫よりも、この早期終了（Wang・Yu・Long が ICDE'25 で一般化した考え方の最も単純な場合[^et]）の方が大きく効く。

[^et]: K. Wang, K. Yu, C. Long, "Maximal Clique Enumeration with Hybrid Branching and Early Termination," ICDE 2025. <https://arxiv.org/abs/2412.08218>

#### 追加実験: 早期終了を実装して測る

`src/parallel_processing/eppstein_et.py` に、「P がクリークなら R ∪ P を直接答える」判定を入れた。
Tomita のピボット（P ∪ X のうち P を最も多く見る頂点）が P の |P| − 1 個を見ていなければ P はクリークではないので、まずその 1 回の積集合で絞り、通ったときだけ全頂点を調べる。
判定を入れる場所は二通り試した。

- **全呼び出し**: 再帰のすべての呼び出しで判定する
- **根だけ**: 外側ループの各頂点の部分問題（根）でだけ判定し、その下は元の探索のまま

出力は元の Eppstein と完全に一致する（テスト 60 件）。
同じプロセスで 3 つを交互に 5 回ずつ（soc は 3 回ずつ）走らせた最小値は次のとおり（`artifacts/linux/early-termination-v2.log`）。

| グラフ | 極大クリーク数 | Eppstein | 全呼び出し | 倍率 | 根だけ | 倍率 |
|---|---|---|---|---|---|---|
| 木 n=20k | 19,999 | 0.088 s | 0.091 s | 0.96 | 0.087 s | 1.01 |
| 2 次元格子 100×100 | 19,800 | 0.053 s | 0.056 s | 0.94 | 0.056 s | 0.94 |
| 疎 ER n=20k | 99,692 | 0.382 s | 0.394 s | 0.97 | 0.396 s | 0.96 |
| BA m=5 | 96,947 | 0.343 s | 0.361 s | 0.95 | 0.358 s | 0.96 |
| 密 ER n=120 | 34,965 | 0.211 s | 0.230 s | 0.92 | 0.218 s | 0.96 |
| Moon–Moser k=11 | 177,147 | 0.250 s | 0.284 s | 0.88 | 0.268 s | 0.93 |
| ca-HepPh | 14,939 | 1.368 s | 1.110 s | 1.23 | 1.104 s | **1.24** |
| ca-AstroPh | 36,428 | 1.871 s | 1.771 s | 1.06 | 1.732 s | **1.08** |
| soc-sign-epinions（3 回） | 22,226,173 | 202.6 s | 213.8 s | 0.95 | 201.9 s | **1.00** |

**根だけで判定する形が、損をせずに効果をすべて取った。**
ca-HepPh と ca-AstroPh の伸びは全呼び出しと同じで、効果は根での判定からほぼすべて来ている。
全呼び出しでは soc-sign-epinions が 5% 遅くなった（別の実行では 7%）が、根だけなら差がなかった。
小さな合成グラフで残る数%の損は、ミリ秒単位の差であり、再帰に判定用の引数を渡す書き方の分と見られる。
最初の実装はピボットの採点を辞書に保存して再利用したが、辞書を毎回作るコストで合成グラフが 9〜17% 遅くなったので、絞り込み方式に改めた。

ca-HepPh の伸びが「P がクリークの頂点が仕事の 56%」から期待するより小さいのは、大きく縮むのが最重の 1 頂点（174.7 ms → 9.0 ms）だけで、残りの該当頂点は P が小さく、一本道をたどってもそもそも安いためである。

ca-HepPh の早期終了ありの頂点ごとのコストを取り直すと、最重の頂点が全仕事に占める割合は 13.37% から 0.85% に下がった（合計 1.246 秒 → 0.962 秒）。
シミュレータで並列の伸びを比べると、早期終了なしでは 8 コア以上で 7.48 倍に張り付くのに対し、早期終了ありでは 16 コアで 15.9 倍、32 コアで 31.8 倍とほぼ線形に伸びた（`hetero_analysis et`、実測コスト順の lpt）。
卒論 5 章で「ca-HepPh は 1 頂点が 13% を占めるので上限が約 7.7 倍」とした制約は、並列化ではなくアルゴリズム側の工夫で消える。
M4 の形（10 コア、速さの和 6.58）はもともとこの上限の下にあるので、差が出るのはもっと大きなマシンである。


## シミュレータによる拡張（4 コアを超える構成と、一定でない r）

実測は 4 worker までなので、M4 と同じ 4 速い + 6 遅いの構成と、r が一定でない場合をシミュレータで調べた。
コストはこの環境の実測値（計 197.7 秒）で、値は完了時間 ÷ 下限である。
下限には、速さの違う機械で仕事を途中で切って移してよい場合の最適値（Q|pmtn|Cmax）を使った[^pmtn]。
これは「重い順に k 個の仕事は、速い順に k 個のコアの速さの和で割った時間より早くは終わらない」という値の k についての最大で、どんな配り方でもこれより速くはできない。
1.000 はどんな配り方でもこれ以上速くできないことを表す。

[^pmtn]: E. C. Horvath, S. Lam, R. Sethi, "A Level Algorithm for Preemptive Scheduling," J. ACM 24(1), 1977; T. Gonzalez, S. Sahni, "Preemptive Scheduling of Uniform Processor Systems," J. ACM 25(1), 1978.

### r を見誤った静的配分

静的 LPT に実測コスト（最良ケース）を与え、遅いコアの速さだけを間違えた。
値は同じ構成の lpt（動的）に対する完了時間の比で、1 を超えると動的に負ける。

| 構成 | 真の r | 入れた r=0.15 | 0.26 | 0.35 | 0.43 | 0.5 | 0.6 | 0.75 | 1.0 |
|---|---|---|---|---|---|---|---|---|---|
| 4F+6S | 0.26 | 0.987 | 0.869 | 1.067 | 1.215 | 1.328 | 1.468 | 1.640 | 1.859 |
| 4F+6S | 0.43 | 1.266 | 1.116 | 1.017 | 0.943 | 1.031 | 1.139 | 1.273 | 1.443 |

| F,F,S,S | 0.43 | 1.223 | 1.117 | 1.042 | 0.984 | 1.091 | 1.227 | 1.402 | 1.636 |

正しい r を入れたときだけ、静的 LPT は動的より 2〜13% 速い。
r を 0.43 と 0.26 で取り違えるだけで（卒論の推定値と下限値の差）、動的に 12〜22% 負ける。
非対称を無視して r = 1 を入れると、動的の 1.2〜1.9 倍かかる。
しかも静的 LPT のコストを |P| からの予測値にすると、正しい r でも下限の 1.04〜1.29 倍に落ち、lpt（動的）より悪くなる構成が多い。
静的配分は、コストと速さの二つを同時に正確に知っているときにしか勝てない。

### 一定でない r（M4 の形、公称 r = 0.43）

| 配り方 | r 一定 | H3（速いコアは忙しいほど遅い） | H4（タスクで r が違う） | H3 + H4 |
|---|---|---|---|---|
| interleave | 30.2 s | 34.5 s | 27.8 s | 31.2 s |
| lpt（動的） | 31.9 s | 35.0 s | 29.2 s | 31.1 s |
| 静的 LPT（r = 0.43 を仮定） | 30.0 s | 38.0 s | 30.0 s | 38.0 s |
| 静的 LPT（r = 0.54 を仮定） | 34.3 s | 34.6 s | 27.4 s | 34.6 s |

H3 は、速いコアが 1 個増えるごとに 7% 遅くなるモデル（4 個で 0.79、M4 の P コアのみ並列の効率）である。
このとき全部が動いている間の実効的な比は 0.43 ÷ 0.79 ≈ 0.54 になる。
H4 は、重いタスクほどメモリ待ちが多いと仮定し、計算の割合 α を最も軽いタスクの 1.0 から最も重いタスクの 0.6 まで変え、遅いコアの速さを 1 ÷ (α ÷ r + 1 − α) としたモデルである（根拠のない仮定であり、感度を見るためのもの）。

r が一定なら静的 LPT が最速だが、H3 が入ると静的 LPT（r = 0.43）は interleave より 10% 遅くなり、H3 + H4 では 22% 遅くなる。
H3 を見越して r = 0.54 を入れた静的 LPT は、H3 だけなら追いつくが、r 一定の場合には 14% 負ける。
一つの r では、変わる r に合わせられない。
動的な配り方（interleave、lpt）は、どの場合も最良の 1.1 倍以内にとどまった。

## 関連研究との位置づけ

- **速さの違う機械へのスケジューリング**（uniform machines, Q||Cmax）: 本実験の静的 LPT は、Gonzalez・Ibarra・Sahni（SIAM J. Comput. 1977）が解析した「重い順に、最も早く終わる機械へ」の LPT そのものである[^gis]。LPT は機械の速さが既知であることを前提にした近似アルゴリズムで、本実験はその前提（r とコストが正確に分かる）が崩れたときの損を測ったことになる
- **速さの違うプロセッサ上の work stealing**: Bender と Rabin は Cilk のプログラムを速さの違うプロセッサで実行する問題を理論的に扱った[^br]。Torng らの AAWS は、静的な非対称（コアの種類）と動的な非対称（DVFS）の両方を考慮した work stealing を提案した[^aaws]。WATS は非対称マルチコア向けに、タスクの重さを見て盗む先を選ぶ方針を評価した[^wats]。本実験の「速いコア専用キュー（giants）」は、これらの考え方を最も単純にしたものである
- **OS による非対称コア間の移動**: Linux にも、容量の小さい CPU で詰まっているタスク（misfit task）を、より容量の大きい CPU へ能動的に移す仕組みがある[^cap]。H5 で macOS について仮定した「空いた速いコアへの移動」は macOS 特有の振る舞いではなく、非対称コアを持つ OS に一般的な設計である。したがって「worker の idle と速いコアの idle が一致しない」という指摘は、Linux のハイブリッド CPU（Intel の P/E コアなど）にもそのまま当てはまるはずである（未検証）

[^gis]: T. Gonzalez, O. H. Ibarra, S. Sahni, "Bounds for LPT Schedules on Uniform Processors," SIAM J. Comput. 6(1), 1977. <https://sites.cs.ucsb.edu/~teo/papers/SICOMP-Uni.pdf>
[^br]: M. A. Bender, M. O. Rabin, "Scheduling Cilk multithreaded parallel programs on processors of different speeds," SPAA 2000. <https://dl.acm.org/doi/10.1145/341800.341803>
[^aaws]: C. Torng, M. Wang, C. Batten, "Asymmetry-Aware Work-Stealing Runtimes," ISCA 2016. <https://www.csl.cornell.edu/~moyang/pdfs/torng-aaws-isca2016.pdf>
[^wats]: Q. Chen ほか, "WATS: Workload-Aware Task Scheduling in Asymmetric Multi-core Architectures." <https://www.cs.sjtu.edu.cn/~chen-quan/PDF/Conferences/C11.pdf>
[^cap]: Linux kernel documentation, "Capacity Aware Scheduling"（misfit task migration の節）. <https://docs.kernel.org/scheduler/sched-capacity.html>

## 妥当性への脅威

- **quota はクロック低下と違う**: エミュレーションでは計算もメモリ待ちも同じ割合で遅くなる。実機の E コアでは、メモリ待ちの多いタスクほど遅くなりにくい（卒論 5 章: 純ループ 5.75 倍に対し soc 3.79 倍）。タスクによって r が変わる効果（H4）は、シミュレータでしか扱っていない
- **止まっている間は応答しない**: 遅いコアの worker は最大 (1 − r) × 周期の間、仕事を取りに行けない。動的な配り方に不利に働く歪みで、周期を変えた比較（3c）で大きさを確かめた
- **worker の移動は模倣である**: 移動モードは「速いコアの役を引き継ぐ」ことを上限の書き換えで表しているだけで、実際には CPU を移っていない。キャッシュの移動コストや、macOS がどの worker をいつ移すかの規則は再現していない
- **4 vCPU しかない**: 実測は最大 4 worker である。M4 と同じ 4 速い + 6 遅いの構成はシミュレータでのみ扱った
- **クラウドのノイズ**: steal 時間は除外基準（3%）を soc のすべての run で下回った（ca-HepPh の 1 秒未満の run では 17 本が基準を超えて除外された）。それでも同じ条件の 3 回の間で数%の振れがある
- **実行器の違い**: Phase 3 の pull 実行器は Phase 1 の Pool 実行器より数%遅い（interleave で 75.1 秒対 72.2 秒）。Phase 3 の効率の絶対値は、その分低く出ている
- **測定中の待ちループ**: 較正と Phase 1 の間、`pgrep` で終了を待つシェルが 3 本、5〜20 秒ごとに動いていた（自分自身に一致して終わらない不具合。`artifacts/linux/notes.txt`）。1 回あたり数ミリ秒なので影響は無視できると判断した
- **M4 との対応は未検証**: r の範囲は外部情報からの推定で、本研究では確かめていない。H5 も M4 実機では確かめていない

## 次への示唆

### 1. 卒論の結論の直し方

卒論 5 章は、interleave で idle が消えても速くならなかった原因を「P/E コアの非対称」とし、「idle% はコアの均質性を暗に仮定した指標」と結論している。
本実験の結果からは、原因は「非対称なコア」と「OS による worker の移動」の組み合わせであり、指標が暗に置いている仮定は「worker とコアが 1 対 1 に対応すること」である。
卒論や発表で引用するときは、この二点を言い直すのがよい（ただし M4 実機では未検証であることを添える）。

### 2. M4 実機で確かめること（H5 の反証可能な予測）

H5 が正しければ、次の測定結果になるはずである。
どれも M4 で 1 時間以内に測れる。

- **背景負荷のない状態で block w=8 を測ると、おおよそ 21〜26 秒になる。** Chrome を閉じた interleave w=8 の 18.2 秒より 15〜40% 遅いはずで、卒論の「4.3% しか縮まない」は背景負荷と移動の両方で差が縮んで見えていたことになる（値は競合を入れないシミュの r = 0.26〜0.43 の範囲）
- **w=4（P コアの数以下）で背景負荷がなければ、interleave は block より 1.2〜1.3 倍速い。** 4 worker が全員 P コアに乗れば移動の余地がなく、固定と同じ振る舞いになるはずである（競合なしのシミュで block 32.5 秒、interleave 24.5 秒。block は終盤に働く P コアが減って競合が軽くなる分、差は少し縮むと見込む）
- **powermetrics でクラスタ別の稼働率を見ると、block でも P クラスタはほぼ終わりまで 100% 近く稼働している。** worker の idle は E クラスタの遊休として現れるはずである

### 3. Linux のハイブリッド CPU で確かめること

Linux にも非対称コア間の移動（misfit task migration）がある。
Intel の P/E コアを持つ Linux マシンなら、`taskset` で固定した場合と固定しない場合を同じコードで比べられ、エミュレーションではなく本物のクロック差で H5 を検証できる。
`/proc/stat` の CPU ごとの稼働時間を記録すれば、「worker の idle」と「コアの idle」の差を直接観測できる。

### 4. 測り方

- worker ごとの idle ではなく、**コアごとの稼働率**（Linux は `/proc/stat` の CPU 別、macOS は powermetrics のクラスタ別）を記録する。worker とコアが対応しない環境では、worker の idle は無駄の量を表さない
- **r は並列に動かしたまま測る。** 1 コアで測った r（0.42）は、4 コアで同時に動かしたときの r（0.39〜0.41）と 2〜7% 違った。静的配分のパラメータにするなら、実行中の実効値でなければ意味がない

### 5. 配り方の設計

- 非対称なコアでは、**r を使わない動的な配り方（重さを混ぜるか、細かく配る）を既定にする。** 速さで重み付けた静的配分は、コストと r の両方を正確に、しかも実行中の値で知っているときにしか勝てず、その条件は実際にはまず満たせない
- r を使いたいなら、実行中に各コアの進み具合から推定し直す**適応的な配分**が次の候補になる（本実験では未実装）
- 偏りをならせる配り方なら、**遅いコアも含めて全コアに worker を置く。** ならせない配り方のまま worker を増やすのは逆効果になりうる
- OS の移動は偏った配り方の損を半分以下に減らすが、ゼロにはしない。「移動に任せれば配り方は何でもよい」わけではない

### 6. アルゴリズム側の改善（並列化より先にやる価値があるもの）

- **候補集合がクリークなら直接答える早期終了を、外側ループの根で入れる。** 試作（`eppstein_et.py` の `deep=False`）で逐次の ca-HepPh が 1.24 倍、ca-AstroPh が 1.08 倍速くなり、soc-sign-epinions では損がなかった（全呼び出しで判定すると soc は 5〜7% 遅い）。`eppstein.py` 本体と並列版に取り込むのが次の一歩である。Wang・Yu・Long の手法は、この考え方をクリークに近い形まで広げたものである
- 早期終了は並列版にも入れられる。ca-HepPh では最重の頂点が全体の 13.37% から 0.85% になり、シミュレータでは 32 コアで 31.8 倍まで伸びた（早期終了なしは 7.48 倍で頭打ち）。実測での確認は、4 コアより大きいマシンが要る
- 卒論の今後の課題にあった「ca-HepPh 型の単一重部分問題の内部分割」は、少なくとも ca-HepPh では不要になる。重い頂点が一本道なので分けようがなく、早期終了で消える
- コストの予測子（|P|）は順位相関 0.86 で、上位 1% の捕まえ方が弱い（65%）。予測順の lpt と実測順の lpt の差は、M4 の形のシミュで最大 13%（r = 0.26）あった。P 内の辺の数など、安く測れて精度の高い予測子を探す価値がある

### 7. 理論との接続

OS の移動は、仕事を途中で速いコアへ移すことなので、非 preemptive な配分を preemptive に近づける。
速さの違う機械の preemptive スケジューリング（Q|pmtn|Cmax）は最適解が効率よく求まることが知られており、本実験の下限にも使った。
「OS が移動してくれることを前提に、アプリケーション側の配り方は何をすればよいか」は、理論と実装の両面から問える次の研究課題である。
たとえば worker をコア数より多く置いて OS に移動させることが、アプリケーション側の動的配分の代わりになるかどうかは、まだ調べていない。
