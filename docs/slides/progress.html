途中経過

ここまでの進み方

極大クリークを全部出す計算を、測りながら並列にしてきた。

論文として閉じた主張ではない。測った順に、何を見て次を決めたかを話す。

今日の順

1最初に測ったもの
2逐次で比べる
3外側を配る
4止まった理由を潰す

数字は、その場の条件と一緒に出す。別の日、別の機械の数字は並べて倍率にしない。

1 何を数えているか

互いに全部つながった頂点の集まりがクリーク。

どれを足してもクリークでなくなるものが、極大クリーク。

この研究は、その極大クリークを全部出す。一番大きいものを 1 個だけ探す問題ではない。

定義は卒論第 2 章。主対象の soc-sign-epinions は頂点 131,828、極大クリーク約 2,223 万。

1 最初に測ったアルゴリズム

Tomita らの CLIQUES

Bron–Kerbosch 法に、ピボットで枝を減らす規則を足したもの。卒論の第一歩として、論文の擬似コードに合わせて実装した。

最初の実データの照合先は SNAP の ca-AstroPh。計画の基準は論文の表の 36,427。記録された数は 36,428 で、1 多い。

差は SNAP の頂点数のずれとして扱っている。計画は docs/plans/cliques-benchmark.md。時間の表は卒論第 5 章。

1 CLIQUES は何をしているか

Q

ここまで育てたクリーク。

SUBG

まだ入れてよい頂点。

CAND

まだ試していない候補。

  • SUBG が空なら、Q は極大クリーク。
  • SUBG から、CAND を一番多く見ている頂点をピボットに選ぶ。
  • ピボットの隣は、この段では試さない。
  • 試した候補は CAND から外す。次の兄弟は、それを処理済みとして扱う。

実装は src/parallel_processing/cliques.py。基本の Bron–Kerbosch は正しさの照合用で、この実測の対象ではない。

2 次に足した Eppstein

外側の順番だけを変える。内側は同じピボット探索。

  1. その時点で次数が最小の頂点を、繰り返し剥がす。この順が縮退順序。
  2. 各頂点について、自分より後ろの隣だけを候補にする。
  3. その部分問題の中は、CLIQUES と同じピボットで探す。

疎なグラフでは、外側の候補が小さくなる。各頂点の部分問題は、互いに独立。

Eppstein, Löffler, Strash。実装は eppstein.py。出力するクリーク集合は CLIQUES と一致させる。

3 並列の切り方

縮退順序の各頂点を根にする部分問題を、バッチにまとめて worker に配る。

内側のピボット探索は、逐次のまま。

この実装は、起動時にグラフ全体を各 worker へ pickle で渡す。配り方はプールの動的割り当て。

eppstein_parallel.py。macOS のプロセス起動は spawn。

4 混ぜても、時間は少ししか縮まない

idle 32.6% → 0.1%

interleave は、重い頂点と軽い頂点を同じバッチに混ぜる。8 worker の compute は 25.9 秒から 24.8 秒。短縮は 4.3%。

働いた時間の合計は 139 秒から 198 秒に増えた。空きを埋めた分、1 単位の仕事が遅くなった。

4 起動時のコピーを減らした

fork にすると、グラフを copy-on-write で受け継ぐ。startup は全 9 グラフで 0.03 秒以下。

spawn では損だった小さいグラフのうち 4 つが、4 worker で約 2 倍の得に転じた。

共有メモリ版の soc、8 worker の total は 26.5 秒。M4 の卒論草稿が置いた到達点。

逐次の 94.9 秒は別セッション。約 3.6 倍は参考値。同じセッションで比べてよいのは fork と共有メモリ。

fork の soc 8 worker total は 31.7 秒。spawn の 37.8 秒も別セッション。

その後 固定すると、空きを消した分だけ速い

64.9 秒 → 51.1 秒

Linux の 4 vCPU を同じ速さに固定した。block 64.9 秒、interleave 51.1 秒。働いた時間の合計は 200 秒と 203 秒でほぼ同じ。

M4 の「空きは消えたが 4.3% しか縮まない」は、コアを固定したこの実験では再現しなかった。

worker がコアの間を移る、という仮説はエミュレーションでは当たった。M4 では測り直していない。

soc、バッチ 64、3 回の最小値。docs/hetero-experiments.md の Phase 1。卒論第 6 章は、まだ P/E の差だけで説明している。

その後 一本道は枝で割れない

ca-HepPh の重い頂点は、候補 238 個が互いに全部つながっている。ピボットを選ぶと枝は 1 本。深さで割っても割れない。

P がクリークなら、その場で答えを 1 個返す。判定は外側の根だけに置く。

いま言えること

  • 最初に測ったのは CLIQUES。ca-AstroPh は 36,428 で、論文の表より 1 多い。
  • 根を割る並列は、2 worker と 4 worker で遅くなった。外側を Eppstein に変えた。
  • バッチを細かくすると、単発の soc 8 worker は 70.0 秒から 27.7 秒。
  • M4 では空きを消しても 4.3%。コアを固定した Linux では、その現象は再現しなかった。
  • M4 の草稿上の到達点は、共有メモリ版の soc 8 worker で total 26.5 秒。条件つき。

まだ言わないこと

  • この結果を、論文として一般化できるとはまだ言わない。
  • fork の compute が共有メモリより遅い理由は、切り分けが済んでいない。
  • E コアの速度比 0.26 は下限。全力のクロックは直接測っていない。
  • M4 の 4.3% を「移動のせい」と言い切らない。エミュレーションでは当たり、M4 の再測定はない。
  • シミュレータの倍率は実測と分ける。32 コアで 31.8 倍、は壁時計の測定ではない。
  • 早期終了は、共著グラフの一本道には効く。soc の並列を速くした測定ではない。
